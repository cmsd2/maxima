Breakpoints in the debugger
============================

This file documents Maxima's breakpoint machinery as implemented in
src/mdebug.lisp and the hooks in src/mlisp.lisp's mdefine and
meval1.


1. What :break does
-------------------

The :break command (and the Lisp-level break-function) accepts
either a function name with an optional line offset, or a source-
file path with a line number.  Each successful call stores a bkpt
struct in *break-point-vector* and prints the breakpoint's index.
A breakpoint records the source file, the absolute line number,
and a direct reference to the parsed form at that line.


2. Resolution
-------------

When the target is a function name, break-function looks the
function up via (mgetl fun '(mexpr mmacro)), retrieves its lineinfo
via get-lineinfo, computes the requested line (function start +
offset, or the supplied line if absolute is set), and walks the
parsed body with first-form-line to find the form whose source
line matches.

When the target is a file path, break-function scans the maxima
package for any symbol whose lineinfo names the same file and
whose function spans the requested line, then recurses with the
function name and an absolute line.

If no loaded function references the requested file, the breakpoint
is treated as deferred (section 5).  If the file is found but no
function spans the line (e.g. a comment before the first
definition), break-function fails immediately -- there is nothing
for a future definition to satisfy.


3. How meval1 fires breakpoints
-------------------------------

Inside meval1's main dispatch, a cond clause checks each cons form
against the entries in *break-points* using object identity (eq).
A match invokes the break loop.  Two consequences follow:

  - Redefinition invalidates breakpoints.  A reloaded function's
    body consists of fresh cons cells, so old breakpoint references
    are stale.  See section 8 for how re-application handles this.

  - Some forms never fire.  meval1 dispatches mplus, mtimes, mexpt,
    and mnctimes before reaching the breakpoint check, as a fast
    path for arithmetic.  A breakpoint set on a line whose top-level
    form is one of these is registered but never triggered.


4. Lineinfo and non-executable lines
------------------------------------

set-full-lineinfo (mlisp.lisp) builds a per-function vector with
one slot per source line.  walk-get-lineinfo records the first
form encountered on each line and explicitly fills gaps with nil.
Lines that produce no evaluable form -- blank lines, comments,
lone closing parens, an "else" keyword on its own line, and so on
-- get nil entries.  A breakpoint requested on such a line can
never fire because meval1 will never visit it.  Line snapping
(section 6) addresses this case.


5. Deferred breakpoints
-----------------------

If :break is given a file path that no loaded function's lineinfo
references, the breakpoint is stored in *pending-breakpoints* (a
list of (file line) pairs) and resolution is deferred.  After every
mdefine, resolve-pending-breakpoints checks the newly-defined
function's source file against the pending list; matches are
removed and re-submitted to break-function so the normal resolution
path runs.  Entries that still don't resolve stay on the list.

The :pending debugger command lists unresolved entries.


6. Line snapping
----------------

nearest-executable-line wraps first-form-line with a bidirectional
search: if the requested line is empty it scans outward, alternating
directions, up to *nearest-executable-line-search-radius* lines
(default 50) each way.  When a snap occurs the new line is reported
back to the user.

Stepping is unchanged.  The stepper stops on whichever form meval1
next evaluates, so non-executable lines are naturally skipped during
step-into/step-next.


7. Path normalization
---------------------

User-supplied paths to :break may be relative, absolute, or go
through symlinks; the lineinfo path stored at load time is whatever
(probe-file ...) returned at parse time.  canonical-pathname-string
(commac.lisp) canonicalizes both sides through probe-file before
comparison.  Pending entries retain the original user string at
defer time (the file may not exist yet) and canonicalize only on
resolution.


8. Re-application on redefinition
---------------------------------

reapply-breakpoints-for-function is called from mdefine just after
mputprop installs the new mexpr.  It collects the absolute line
numbers of the function's existing breakpoints, deletes the stale
entries, and re-issues each one against the new definition
(snapping if the line shifted).  It runs before resolve-pending-
breakpoints so the two passes don't interfere.


9. Maxima-level interface
-------------------------

Six Maxima-callable functions support programmatic use and the test
suite:

  set_breakpoint(fun, li)     set or defer a breakpoint;
                              returns the breakpoint index or -1
  breakpoint_line(n)          absolute file line of breakpoint n
  pending_breakpoints()       pending entries as a Maxima list
  breakpoint_count()          number of breakpoint entries
  valid_breakpoint_count()    number of non-stale entries
  clear_breakpoints()         delete all active and pending bps

See tests/rtest_debugger.mac for usage examples.


10. Location reporting at the prompt
------------------------------------

On entry to the break loop, a "file:line::" line is printed
before the debug prompt.  Normally this comes from frame 0's
lineinfo (top of *mlambda-call-stack*).  At the top level
(empty stack, e.g. a runtime error outside any user function),
the location is taken from *last-meval1-form* instead.
:frame 0 has the same fallback.


11. Known gaps
--------------

a) Bare arithmetic forms (mplus, mtimes, mexpt, mnctimes) never
   trigger breakpoints (section 3).

b) Macro definitions (mdefmacro) bypass the resolver hook, so
   deferred breakpoints aimed at macros do not resolve.
